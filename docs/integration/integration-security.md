# Integration Security

## Purpose

This document defines the security baseline for all platform integrations.

Integration security is governed by Chapter 9 and specialized here for
external systems, public APIs, webhooks, adapters, and provider credentials.

## Mandatory Controls

Every integration must use:

- TLS.
- Authentication.
- Authorization.
- Input validation.
- Rate limiting.
- Safe errors.
- Secret management.
- Audit.
- Observability.
- Data classification.
- Need-to-Know restrictions when content is involved.

## Identity and Authorization

Integration requests must use server-derived identity, approved API keys,
OAuth/OIDC tokens, webhook signatures, or equivalent approved credentials.

Client-provided identity, tenant IDs, organization IDs, roles, or permissions
must not be trusted for authorization.

## API Keys

API keys must:

- Be generated by Gateway or approved IAM infrastructure.
- Be scoped.
- Be revocable.
- Have expiration where policy requires it.
- Store only hashes or encrypted values.
- Be audited on creation, use where applicable, and revocation.

## OAuth and OIDC

OAuth and OIDC integrations must:

- Be registered through IAM or Integration Gateway.
- Store client secrets through Secret Management.
- Validate issuer, audience, expiration, and scopes.
- Map external identity to internal users, organizations, workspaces, roles,
  and permissions.
- Preserve audit and traceability.

## Webhooks

Webhooks must:

- Use HTTPS.
- Verify signatures.
- Use replay protection.
- Validate payload schemas.
- Record delivery logs.
- Audit configuration and state-changing results.

## Provider Secrets

Provider credentials must not appear in:

- Source code.
- Logs.
- Traces.
- Client bundles.
- JSON Master.
- Export artifacts.
- Webhook delivery logs.
- Error messages.

Secrets are stored only through approved secret management or external vault
integration when approved.

## Data Classification

Before sending data to an external provider, the platform must evaluate:

- Classification level.
- Organization policy.
- Workspace policy.
- Need-to-Know scope.
- Provider privacy policy.
- Retention policy.
- User authorization.
- Human approval requirement when configured.

`RESTRICTED` content must not be sent to external providers unless an explicit
approved policy allows it.

## CORS and CSRF

Browser-facing APIs must use documented CORS policy.

Cookie or browser-session flows must include CSRF protection where applicable.

## Audit and Observability

Audit records explain who authorized or changed an integration.

Observability records explain how integration execution behaved.

Both are required. Neither replaces the other.
