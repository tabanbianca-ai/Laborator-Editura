# Frontend Internationalization

## Purpose

This document defines frontend internationalization rules for Platform
Language.

Platform Language controls UI language only. It must not change Original
Language, Authoring Language, or Target Language.

## Supported Initial Languages

Initial UI languages:

- Romanian.
- English.
- Spanish.
- French.
- Portuguese.
- Italian.
- German.

The architecture must allow adding more languages without changing
application code.

## Current Baseline

The current frontend includes:

- `apps/web/lib/ui-i18n.ts`.
- `UiLocale` for `en`, `ro`, `es`, `fr`, `pt`, `it`, and `de`.
- Platform Language resolution with fallback to English.
- Translated labels for major navigation, auth, dashboard, pipeline,
  distribution, roles, language metadata, and workflow labels.
- AppShell uses Workspace preferences to set `lang` and translator context.
- Sidebar and TopNav use translated labels.

## Required Rules

- All user-visible text must come from translation resources.
- Components must not embed visible labels, messages, helper text, aria labels,
  loading labels, empty-state text, or error text directly.
- Missing keys must fall back to English.
- Platform Language switching must not alter manuscript, original, authoring,
  or target language metadata.
- AI-facing frontend explanations must use Platform Language.
- User content, manuscript text, source text, target translation, quotes, and
  imported documents must not be translated as UI text.

## Current Gaps

- Some page, editor, loading, option, and placeholder strings remain embedded
  directly in components.
- Several non-English dictionaries are fallback-style and do not yet provide
  complete UI coverage.
- Translation completeness reporting exists as metadata but is not yet enforced
  by tests for every route.
- Some ARIA labels and progress labels are dynamically composed in English.

## Translation Resource Contract

Each translation key should preserve:

- Key.
- English fallback.
- Romanian translation.
- Target language translations.
- Context or description where ambiguity exists.
- Domain when platform-specific.
- Status: draft, reviewed, validated.
- Last updated date.

## Testing Strategy

Frontend i18n tests should verify:

- No user-visible hardcoded strings in production components.
- All routes render with supported Platform Languages.
- Missing labels fall back to English.
- Platform Language does not mutate content language metadata.
- Navigation, forms, empty states, errors, and action labels are translated.
- ARIA labels and loading states use i18n resources.

## Migration Rule

Hardcoded text must be replaced incrementally with i18n keys while preserving
existing behavior and validated Phase 7 Step 16 functionality.
