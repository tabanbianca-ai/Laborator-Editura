# Codex Versioning

Codex Versioning governs how architecture documents, module specifications,
standards, reference models, dependencies, and governance decisions evolve.

## Versioned Items

Versioned items include:

- Codex releases.
- Architecture chapters.
- Module specifications.
- Reference models.
- API contracts.
- Event contracts.
- Standards.
- Governance policies.
- Migration plans.
- Architecture decisions.
- Exceptions.

## Version Record

Each Codex version should include:

- Version identifier.
- Publication date.
- Published by.
- Included documents.
- Changed modules.
- Changed standards.
- Compatibility notes.
- Migration notes.
- Validation evidence.
- Audit references.

## Versioning Rules

- Versions cannot erase history.
- Previous versions remain auditable.
- Breaking changes require migration notes.
- Deprecated elements must remain traceable.
- Published versions require approval.
- AI may compare versions but may not publish versions.

## Compatibility

Compatibility must be assessed across:

- Modules.
- APIs.
- Events.
- Data models.
- Workflows.
- AI agents.
- Configuration.
- Security.
- Compliance.
- Documentation.

## Current Baseline

The repository is versioned through Git and Markdown documentation. There is
not yet a formal Codex version registry with compatibility metadata,
publication records, and validation evidence.

## Migration Guidance

Future implementation should:

1. Define Codex release identifiers.
2. Link Codex versions to commits.
3. Store compatibility notes.
4. Link validation evidence.
5. Publish version comparison reports.
