# Laborator Editura Official Platform Architecture

Chapter 8 - Workflow Engine and Editorial Process Architecture.

Official architecture document.

Version: 1.0.

## 1. Purpose

This document defines the official Workflow Engine architecture for the
Laborator Editura platform.

The Workflow Engine coordinates editorial and administrative processes across
the platform. It does not own the business rules of each module. It coordinates
their execution through versioned definitions, instances, stages, transitions,
tasks, assignments, approvals, notifications, deadlines, events, and audit.

This document is an architecture standard. It does not authorize immediate
runtime refactoring, API changes, database changes, UI changes, Docker
changes, or replacement of validated Phase 7 Step 16 behavior.

## 2. Fundamental Principles

Workflow Engine must follow:

- Process Driven Architecture.
- Event Driven Architecture.
- State Machine.
- Human in the Loop.
- AI Assisted Workflow.
- Configurable without Code.
- Audit by Default.
- Versioned Workflows.
- Role Based Execution.

Workflow is a platform coordination layer. It must not become duplicated
business logic inside individual modules.

## 3. Role of Workflow Engine

Workflow Engine is responsible for:

- Coordinating stages.
- Managing transitions between stages.
- Assigning responsible users, roles, or teams.
- Coordinating approvals.
- Triggering notifications.
- Requesting AI executions through AI Orchestration.
- Managing deadlines.
- Managing escalations.
- Coordinating safe automation.
- Recording history.
- Enforcing workflow-level permissions.

Domain modules remain responsible for their own validation rules and persisted
domain state.

## 4. Work Table

Romanian UI label:

- Masă de lucru.

Internal implementation name:

- Work Table.

Work Table is not a separate workflow module. It is the user interface where
users execute tasks and actions generated by Workflow Engine.

Workflow Engine owns process coordination. Work Table presents the user's
current authorized work based on role, task, project, document, workflow stage,
Need-to-Know scope, and permissions.

## 5. Main Entities

Workflow Engine manages the following conceptual entities:

- `WorkflowDefinition`.
- `WorkflowVersion`.
- `WorkflowInstance`.
- `WorkflowStage`.
- `WorkflowTransition`.
- `WorkflowAction`.
- `WorkflowCondition`.
- `WorkflowTask`.
- `WorkflowAssignment`.
- `WorkflowApproval`.
- `WorkflowNotification`.
- `WorkflowDeadline`.
- `WorkflowHistory`.

These entities define the target architecture. Existing runtime entities may
be mapped incrementally.

## 6. WorkflowDefinition

`WorkflowDefinition` defines the process model.

Required fields:

- Identifier.
- Name.
- Description.
- Category.
- Current version.
- Status.
- Author.

Examples:

- Translation Workflow.
- Magazine Workflow.
- Publishing Workflow.
- Children's Book Workflow.
- Review Workflow.
- Audiobook Workflow.
- Video Workflow.

## 7. WorkflowVersion

Every workflow definition change creates a new version.

Workflow versions are immutable. Existing workflow instances continue using
the workflow version with which they were created.

Workflow version records must preserve:

- Version number.
- Definition reference.
- Stage definitions.
- Transition definitions.
- Condition definitions.
- Task templates.
- Approval rules.
- Notification rules.
- Deadline rules.
- Created by.
- Created at.
- Approval metadata when required.

## 8. WorkflowInstance

`WorkflowInstance` represents one concrete execution of a workflow.

Example:

- Translation Project #153.

Each instance must record:

- Definition ID.
- Workflow version ID.
- Organization.
- Project.
- Document, manuscript, publication, or resource scope.
- Current stage.
- Current status.
- Started by.
- Started at.
- Completed at when applicable.
- Paused, blocked, or cancelled metadata when applicable.

An instance must not switch workflow version during execution.

## 9. WorkflowStage

Examples:

- Draft.
- Translation.
- Review.
- Correction.
- Approval.
- Layout.
- Export.
- Technical Validation.
- Publication.
- Completed.

Each stage defines:

- Responsible role or assignment rule.
- Permissions.
- Entry rules.
- Exit rules.
- Estimated duration.
- SLA.
- Allowed actions.
- Allowed AI assistance.
- Required approvals.
- Notifications.
- Deadline behavior.

## 10. WorkflowTransition

Transitions define how an instance moves from one stage or status to another.

Examples:

```text
Draft -> Translation
Review -> Correction
Approval -> Publication
```

Every transition must define:

- Source stage or status.
- Target stage or status.
- Required permissions.
- Conditions.
- Blocking rules.
- Audit action.
- Optional notification events.
- Optional automation triggers.

Invalid transitions must be rejected.

## 11. WorkflowCondition

Workflow Engine supports condition logic:

- `IF`.
- `THEN`.
- `ELSE`.
- `AND`.
- `OR`.
- `NOT`.

Example:

```text
IF Translation Approved
THEN Move to Review
```

Conditions may read domain validation results, but they must not duplicate the
domain logic that produced those results.

## 12. WorkflowTask

Every workflow stage may generate one or more tasks.

A task contains:

- Title.
- Description.
- Responsible user, role, team, or assignment rule.
- Deadline.
- Priority.
- Status.
- Scope reference.
- Allowed actions.
- Related workflow instance.
- Related stage.
- Audit metadata.

## 13. WorkflowAssignment

Workflow Engine supports:

- Manual assignment.
- Automatic assignment.
- Assignment by role.
- Assignment by competence.
- Assignment by team.
- Assignment by workspace.
- Assignment by project scope.
- Assignment by document, chapter, section, or segment scope.

Assignments must respect RBAC, subscription entitlements where applicable, and
Need-to-Know scope.

## 14. WorkflowApproval

Workflow Engine must support:

- Single approval.
- Multiple approvals.
- Parallel approval.
- Sequential approval.
- Veto.
- AI-assisted recommendation.
- Human approval.

AI may recommend or validate. Only authorized humans may grant final approval.

Approval records must preserve:

- Required approver role.
- Assigned approver.
- Decision.
- Decision time.
- Reason.
- Evidence references.
- Version.
- Audit event.

## 15. AI Executions

Workflow Engine may request AI executions for:

- Translation.
- Proofreading.
- Summarization.
- Illustration assistance.
- Audio assistance.
- Video assistance.
- Classification.
- Recommendation.
- Quality validation.

AI execution must happen exclusively through AI Orchestration as defined in
`docs/ARCHITECTURE_CHAPTER_7.md`.

Workflow Engine must not call AI providers directly.

Workflow Engine emits events.

Examples:

- `workflow.started`.
- `workflow.completed`.
- `workflow.failed`.
- `workflow.blocked`.
- `workflow.unblocked`.
- `workflow.cancelled`.
- `stage.entered`.
- `stage.exited`.
- `task.created`.
- `task.assigned`.
- `task.completed`.
- `approval.requested`.
- `approval.granted`.
- `approval.rejected`.
- `deadline.exceeded`.
- `deadline.changed`.
- `automation.triggered`.

Events must be documented, versioned when their contract changes, and
auditable.

## 17. Automation

Workflow Engine may trigger safe automation.

Example:

```text
On translation approval
  -> Create proofreading task
```

Automation rules must be:

- Configurable without code.
- Auditable.
- Permission-aware.
- Reversible where the domain allows it.
- Blocked from bypassing human approvals.
- Blocked from publishing automatically.

## 18. Escalation

Workflow Engine must support escalation through:

- Notifications.
- Reassignment.
- Priority changes.
- Administrator warning.
- Publication blocking.
- SLA breach reporting.

Escalation must be auditable and must not override rights, security, or human
approval rules.

## 19. Parallelism

Workflow Engine must support:

- Parallel tasks.
- Parallel approvals.
- Synchronization.
- Join points.
- Waiting states.
- Blocking states.

Parallel workflow branches must be explicit in the workflow definition and
must preserve audit order.

## 20. Calendar and Agenda

Workflow Engine uses the Scheduling and Agenda capabilities for:

- Deadlines.
- Meetings.
- Notifications.
- Recurrences.
- Editorial calendars.
- AI task scheduling.

Workflow Engine must not implement a separate calendar.

## 21. Audit

Workflow audit must cover:

- Workflow definition changes.
- Workflow version creation.
- Workflow instance creation.
- Stage changes.
- Status changes.
- Assignment changes.
- Approvals.
- Rejections.
- Task creation and completion.
- Deadline creation and change.
- Deadline breaches.
- Notifications.
- AI execution requests.
- Automation triggers.
- Escalations.
- Manual overrides.

Audit must preserve actor, organization, scope, before state, after state,
timestamp, reason, and related event references where applicable.

## 22. Versioning

`WorkflowDefinition` is versioned.

`WorkflowInstance` uses a fixed workflow version for its full execution.

Changing a definition creates a new version and must not rewrite active or
historical instances.

## 23. Permissions

Every workflow action must be authorized through the central RBAC and
Need-to-Know access model.

Example permissions:

- `workflow.start`.
- `workflow.pause`.
- `workflow.resume`.
- `workflow.cancel`.
- `workflow.configure`.
- `workflow.approve`.
- `workflow.assign`.
- `workflow.escalate`.
- `workflow.override`.
- `workflow.view_history`.

Permission checks must happen server-side.

## 24. Observability

Workflow Engine must expose:

- Average execution time.
- Stage duration.
- Bottlenecks.
- Pending tasks.
- Overdue tasks.
- SLA status.
- Approval latency.
- AI usage triggered by workflow.
- Productivity indicators.
- Error rates.
- Blocked workflow count.

Observability must not expose restricted content.

## 25. Acceptance Criteria

Workflow Engine is compliant when:

- It supports configurable processes.
- It manages states and transitions.
- It separates workflow definitions from workflow instances.
- It versions workflow definitions.
- It keeps existing instances bound to their original workflow version.
- It integrates AI only through AI Orchestration.
- It uses Scheduling and Agenda for deadlines and calendar behavior.
- It uses central RBAC and Need-to-Know access for authorization.
- It is fully auditable.
- It is observable.
- It does not duplicate workflow logic across modules.

Objectives:

2. Identify processes implemented inside modules.
3. Detect workflow logic dispersed in code.
4. Identify approval rules.
5. Verify event usage.
6. Inventory existing automations.

## Mandatory Requirement for Codex

Treat this document as the official Workflow Engine architecture standard for
Laborator Editura.

Codex must inspect the current repository and identify workflow-related logic,
state transitions, approval mechanisms, task management, automation rules,
deadlines, notifications, and AI-triggered processes.

Codex must compare the current implementation with this architecture and
produce a gap analysis, dependency map, and incremental migration plan before
structural changes are implemented.

Do not duplicate workflow logic across modules.

Workflow definitions must be versioned. Workflow instances must remain
immutable with respect to their definition version.

All workflow actions must be authorized through the central RBAC system and
must be auditable, observable, and configurable without code.

Validated functionality from Phase 7 - Step 16 must be preserved.
